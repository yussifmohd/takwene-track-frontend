## Phase 0 – Foundation & health check (`001-project-foundation-and-health-check`)

### What was built
A React 19 + TypeScript + Vite single-page app with the app shell, a typed API client generated
from the backend's OpenAPI contract, and one page: a system status page showing API and database
health. Also an nginx container (port 8081) that serves the app and proxies `/api` to the API, and CI.

### Important files
| Path | What it does |
|---|---|
| `src/api/client.ts` | `apiFetch`: the only way to call the API (base `/api`, JSON, token hook, `acceptStatuses`); errors become `ApiError`, network failures `ApiError(0)`. |
| `src/api/problem.ts` | ProblemDetails type, `ApiError`, `parseProblem`, `getFieldErrors` (forms), `describeError` (toasts/error states). |
| `src/api/schema.d.ts` | Types generated by `npm run gen:api` from the backend contract (never hand-edited). |
| `src/api/health.ts` | `getHealth`: treats `503` as data (an unhealthy report), not an error. |
| `src/features/health/hooks/useHealthQuery.ts` | TanStack Query: key `["health"]`, refetch every 30 s while visible, 1 retry. |
| `src/features/health/components/HealthCard.tsx`, `LevelMeter.tsx` | Skeleton while loading, ErrorState with Retry, or the report with a level meter and per-check durations. |
| `src/components/AppShell.tsx` | Header, skip link, main navigation (Tracks/Artists marked coming soon), `<Outlet/>`. |
| `src/components/UserText.tsx` | Renders user-entered text with `dir="auto"` (Arabic/Latin). |
| `src/components/ErrorState.tsx`, `PageHeader.tsx`, `NotFoundPage.tsx` | Shared states and page heading. |
| `src/router.tsx`, `src/main.tsx` | Route tree; providers (QueryClient, router, Toaster). |
| `src/index.css` | Design tokens (indigo ink, saffron accent, teal/rose status, Readex Pro), dark mode via `prefers-color-scheme`. |
| `src/test/` | MSW server (`onUnhandledFrame: "error"`), render helpers, setup. |
| `nginx/default.conf.template`, `Dockerfile`, `docker-compose.yml` | Non-root nginx on 8081, `/api` → `http://api:8080`, CSP and security headers, joins `trackmgmt-net`. |
| `scripts/check-bundle-size.mjs`, `.github/workflows/frontend-ci.yml` | 250 kB gzip budget; CI runs lint, typecheck, tests, build, budget. |

### Request flow: status page
`HomePage` → `HealthCard` → `useHealthQuery` → `getHealth` → `apiFetch("/health", { acceptStatuses: [503] })`
→ `fetch("/api/health")` → nginx proxies to the API → JSON report → `HealthCard` renders the
level meter. A non-503 error or unreachable API → `ApiError` → `ErrorState` with Retry.

### Key decisions and why
- **Types from the backend contract** so the client cannot drift from the API silently.
- **Server state in TanStack Query only**; no copies in stores.
- **Same-origin `/api` through nginx**: no CORS in production, one CSP.
- **Every state designed** (skeleton shaped like the content, error with Retry).

### How to run and test
Start the backend stack first, then `docker compose up --build` → `http://localhost:8081`.
Dev server: `npm ci && npm run dev` (proxies `/api` to `localhost:8080`). Tests: `npm test`
(19 at the end of Phase 0); also `npm run lint`, `npm run typecheck`, `npm run build`.

### Known limitations
- Only the status page; Tracks and Artists are placeholders.
- Fonts load from Google Fonts (allowed in the CSP).

## Phase 1 – Admin sign-in & session (`002-jwt-authentication-and-authorization`)

### What was built
A sign-in page, a persisted session, a route guard for protected pages, an account page, a header
menu (Sign in / email + Sign out), and automatic sign-out on token expiry, on any 401 from the
API, and when another tab signs out.

### Important files
| Path | What it does |
|---|---|
| `src/stores/authStore.ts` | zustand session `{ accessToken, expiresAt, email, roles }` persisted as `trackmgmt.session` (v1); zod-validated on load; key removed when signed out; `signOutReason` kept in memory only. (Load and expiry rules tightened by the fix below.) |
| `src/lib/authSetup.ts` | Wires `apiFetch`: attach the token only while valid; 401 on an authenticated call → `signOut("rejected")`; follows other tabs via the `storage` event. (Clears from other tabs handled since the fix below.) |
| `src/api/auth.ts` | `login` (with `skipAuthHandling`, since a 401 there means wrong credentials) and `getCurrentUser`. |
| `src/features/auth/pages/LoginPage.tsx` + `schemas.ts` | react-hook-form + zod; generic message on 401 (email kept, password cleared + focused); 400 → field errors; 429 → wait time from `Retry-After`; unreachable API message. |
| `src/features/auth/redirect.ts` | `safeRedirect`: only same-origin paths as the return address; `loginPathFor`. |
| `src/features/auth/components/RequireAuth.tsx` | Layout route: signed out → `/login?redirect=<current path>`. Routes under it carry `handle.requiresAuth`. |
| `src/features/auth/pages/AccountPage.tsx` + `hooks/useCurrentUserQuery.ts` | `GET /api/auth/me`: email, role, when the session ends. |
| `src/features/auth/components/AuthMenu.tsx` | Header control; signing out on a protected page first navigates to `/` (with `flushSync`). |
| `src/features/auth/components/SessionWatcher.tsx` | Expiry timer + focus/visibility check, removes `["auth"]` queries, toast saying why the session ended. |

### Request flow: signing in
`LoginPage` (submit) → zod validation → `useLoginMutation` → `login()` → `apiFetch("/auth/login", { method: "POST", skipAuthHandling: true })`
→ nginx → API. On 200: `signIn(session)` stores it (persisted), the page re-renders as
authenticated and `<Navigate>` goes to `safeRedirect(redirect)`. Later calls get
`Authorization: Bearer …` from `getValidAccessToken()`. On 401 the form shows the generic message.

### Key decisions and why
- **Session in localStorage** (agreed trade-off): survives reloads; mitigated by the CSP, no
  `dangerouslySetInnerHTML`, 60-minute tokens, and removal on sign-out. Documented in the README.
- **Sign-out on 401 everywhere except login**, so an expired or revoked token never lingers.
- **Open-redirect protection** on `?redirect=`.
- **`RouterProvider` from `react-router/dom`**, required for `flushSync` (fixes a sign-out race found in a real browser).

### How to run and test
Both compose stacks up → `http://localhost:8081/login`, sign in with `ADMIN__EMAIL`/`ADMIN__PASSWORD`
from the backend `.env`. Tests: `npm test` (81 at the end of Phase 1).

### Known limitations
- No refresh: after 60 minutes the user signs in again.
- Token readable by script on this origin (see the trade-off above).
- jsdom tests cannot show navigation timing; real-browser checks were done with a throwaway
  script, not an automated E2E suite.

## Fix – Sign-out session state after reload (`fix-sign-out-session-state-after-reload`)

### What was fixed
> Note (added in Phase 2): the four items below are real edge cases found while investigating, and
> their tests fail on the old code, but they were not shown to cause the report. The report could not
> be reproduced and turned out to be a UX expectation (see "Sign-out lands on the sign-in page" below).

Bug reported after Phase 1: the header looked half-rendered while the "Signed out" toast showed,
and after sign-out + reload the stored session and the app's state could disagree. Found in real Edge:
1. The toaster sat at top-right, exactly over the header's Sign in / Sign out controls.
2. Rehydration ignored an expired, malformed or unreadable stored session **in memory only**; the
   entry stayed in localStorage (persist only writes on state changes), so storage said "signed in"
   while the header said "Sign in".
3. "Signed in" was computed per component with `Date.now()` inside zustand selectors, which re-run
   only on store changes – components rendered at different moments could disagree near expiry.
4. A `storage` event with `key === null` (another tab cleared storage) was ignored.

### Important files
| Path | Change |
|---|---|
| `src/stores/authStore.ts` | Storage adapter validates on read (schema, version, expiry) and **removes** what it rejects; `useIsAuthenticated` = "store holds a session"; `endExpiredSession()` turns expiry into a store change; `getValidAccessToken()` ends an expired session instead of sending it. |
| `src/features/auth/components/SessionWatcher.tsx` | Timer and focus/visibility checks call `endExpiredSession()`. |
| `src/lib/authSetup.ts` | Storage listener handles `key === null` and reads the stored entry (source of truth) instead of the event payload. |
| `src/components/ui/sonner.tsx` | Toasts fixed at bottom-right (not overridable). |
| `src/features/auth/sessionConsistency.test.tsx` | Reload regression suite: sign-out clears storage; reload signed out/in/expired; header never shows Sign in together with the signed-in controls. |

### Flow: page load with a stored session
`authStore` module loads → persist calls `getItem("trackmgmt.session")` → JSON + zod + version +
expiry check → valid: session in memory, header/guard/login page all signed in → invalid: key removed,
session null everywhere. A session that expires later is ended by the watcher timer, on focus or
visibility, or by the next API call – always through the store, so every component changes together.

### Key decisions and why
- **One source of truth with one rule**: storage holds exactly what memory holds; anything rejected is
  removed where it is rejected, not merely ignored.
- **No clock in selectors**: time-based state must become a store change, or components disagree.
- **Toasts at the bottom**: transient messages must not cover controls that just changed.

### How to run and test
`npm test` (93 tests). Real-browser check: Edge headless via the DevTools protocol (throwaway script)
covering sign-out → reload, two tabs, expired stored session, expiry while open, Back + reload,
storage cleared in another tab, 360 px toast position.

### Known limitations
- Clearing storage in the **same** tab via DevTools is not observable (no event); the next reload or
  API call reconciles.
- The reload tests rebuild the store via `persist.rehydrate()` (the page-load code path), not a full
  module reload.

## Change – Sign-out lands on the sign-in page (`fix-sign-out-redirect-and-screen-state`)

### What changed and why
Reported as "sign-out does not work". Investigation (real Chrome and Edge, headed and headless,
production build and dev server, several widths, refetch races) showed sign-out worked every time,
but it left the admin on the status page, which looks the same signed in or out – so it seemed to do
nothing. Decision (Yousef): every sign-out lands on `/login`.

| Reason | Where the app goes | Explanation |
|---|---|---|
| Sign out (header) | `/login` | "Signed out" toast (bottom-right) |
| Token expired | `/login?redirect=<page>` | "Your session ended…" on the sign-in page |
| API answered 401 | `/login?redirect=<page>` | "Your session is no longer valid…" |
| Signed out in another tab | protected page → `/login?redirect=<page>`; public page stays | note on sign-in page / toast |

### Important files
| Path | Change |
|---|---|
| `src/features/auth/signOutDestination.ts` | Destination per reason + the sign-in page messages. |
| `src/features/auth/components/SessionWatcher.tsx` | The one place that finishes every sign-out: remove `["auth"]` queries → redirect (with `state.signOutReason`) → explain → acknowledge once the new page shows. |
| `src/features/auth/components/RequireAuth.tsx` | Renders nothing while a sign-out is being handled (no stale content, no competing redirect). |
| `src/features/auth/components/AuthMenu.tsx` | Sign out = `signOut("manual")`; no navigation of its own. |
| `src/features/auth/pages/LoginPage.tsx` | Shows the explanation (`role="status"`) after an automatic sign-out. |

### Flow: Sign out on the account page
Click → `signOut("manual")` clears session + `trackmgmt.session` → header and guard re-render at once
(guard shows nothing) → `SessionWatcher` removes the `["auth"]` cache, navigates to `/login`
(replace), toasts "Signed out" → on the new location it acknowledges the reason.

### Key decisions and why
- **Sign-in page after every sign-out**: a visible change the admin can trust.
- **One handler for all reasons** instead of navigation in the button: the expiry, 401 and
  cross-tab paths behave the same way and the guard cannot race the redirect.
- **Return address only after automatic sign-outs** and only through `safeRedirect` (own pages).

### How to run and test
`npm test` (95). Header sign-out from the status page and the account page, expiry and 401 on both
page types, the return after the next sign-in and both cross-tab cases are covered with the real
router and components.

### Known limitations
- A manual sign-out does not remember the page; signing in again goes to the status page.

| `src/components/ui/alert-dialog.tsx` | shadcn alert dialog, written by hand (the CLI adds the unrelated `cn` package). |

### Flow: changing a track's status
Track page (admin) → buttons from `allowedNextStatuses` → "Mark as distributed" opens the confirm
dialog first → `PATCH /api/tracks/{id}/status` → 200: the response replaces the cached detail, lists
are invalidated, toast ("Track submitted" …) → 409 (already changed, not allowed, or a lost race):
toast with the API's reason, the detail is reloaded so the right buttons show → 401: the Phase 1
sign-out, back to this page after signing in.

### Key decisions and why
- **The API decides which moves are allowed** (`allowedNextStatuses`); the page only shows them, so the
  rules live in one place (the backend domain).
- **Filters in the address** so reloads, Back and shared links keep the view; unknown values are
  ignored instead of producing a 400.
- **Own combobox** for the artist picker instead of a package: about 150 lines, follows the WAI-ARIA
  pattern, no new dependency or license to check.
- **Release dates formatted in UTC**: they are calendar dates; local-time formatting would show the day
  before west of Greenwich (tested with `TZ=America/Los_Angeles`).
- **Tracks stay cached after sign-out** (no personal data); artist caches are still dropped (emails).
- **Status vs distributions**: a track distributed by the status change alone has no deliveries and
  the page says so; Phase 4 adds deliveries without changing this page's rules.

### How to run and test
Backend stack up, then `docker compose up --build` here and open http://localhost:8081/.
Tests: `npm test` (200). Real-browser check (Edge over DevTools, scratch script) on the compose stack
with 28 artists and 24 tracks: visitor catalogue, filters (and invalid ones), artist picker search and
pick, reload keeps the artist name, track page, unknown track, sign-in from Add track and back, empty
submit, duplicate ISRC under ISRC, create, submit, confirm and mark as distributed, admin paging, the
status dot, sign-out – desktop light and 400 px dark, no horizontal overflow, no app console errors.

### Known limitations
- No edit or delete for tracks (not in the assignment's API).
- Filters are single-valued (one status, one genre, one artist).
- The artist picker shows at most 10 matches; typing more of the name narrows them.
- Unsaved form input is discarded when leaving the page (no warning).

## Phase 4 – Distribution (`005-track-distribution-to-dsps`)

### What was built
The track page shows where a track was delivered: a table (stacked rows on phones) with platform,
status badge (pending, live, rejected), sent time and answer time ("Waiting" while pending). Admins
get a **Distribute** dialog (a checkbox per platform: never-sent and rejected ones can be chosen,
pending and live ones are disabled with their status) and, on pending rows, **Mark live** /
**Mark rejected** to record the platform's simulated answer. "Mark as distributed", its confirmation
dialog and the "without platform deliveries" text are gone: the API refuses that status change.

### Important files
| Path | What it does |
|---|---|
| `src/features/tracks/components/DistributionsSection.tsx` | Heading + Distribute, the "answers are simulated" note, the deliveries table, answer buttons from `allowedAnswers`, 409 → toast + reload. |
| `src/features/tracks/components/DistributeDialog.tsx` | Distribute button / disabled "Sent to every platform"; the checklist dialog (platforms from `GET /api/dsps`), send, no-op and conflict handling. |
| `src/features/tracks/components/DistributionStatusBadge.tsx` | Word + mark (open ring, dot, struck dot) in saffron / teal / rose. |
| `src/features/tracks/components/StatusControl.tsx` | Submit / Withdraw only; never offers distributed. |
| `src/features/tracks/hooks/useTrackQueries.ts` | `useDistributeTrackMutation`, `useRecordAnswerMutation` (one helper: store the returned track, refresh lists), `useDspsQuery` (cached for good). |
| `src/features/tracks/catalog.ts` | Delivery status labels and answer words, typed against the contract. |
| `src/api/tracks.ts`, `src/api/dsps.ts` | `distributeTrack`, `recordDistributionAnswer`, `listDsps`. |
| `src/components/ui/dialog.tsx` | shadcn dialog written by hand on `radix-ui` (`alert-dialog.tsx` removed: its only user was the old confirmation). |
| `src/test/server.ts` | `serveTrack()` answers GET/PATCH/distribute/answers for one track using the API's rules; `delivery()`, `DSPS`. |

### Flow: Distribute → page → hook → API
1. `DistributionsSection` shows **Distribute** for admins when the track's `canDistribute` is true.
   `DistributeDialog` reads the platforms (`useDspsQuery`); if every platform is pending or live, the
   button is disabled with "Sent to every platform".
2. In the dialog, the admin ticks platforms; the button names the count.
3. `useDistributeTrackMutation` → `distributeTrack(id, dspIds)` → `POST /api/tracks/{id}/distribute`.
4. The API answers with the updated track; the hook writes it into the detail cache and invalidates the
   track lists (the catalogue badge changes to distributed). The dialog closes with "Sent to N
   platforms", or "Already sent to these platforms" when the track had not changed.
5. `409`/`404` → toast with the API's reason, the detail is refetched, the dialog closes; `401` → the
   usual sign-out to `/login?redirect=…`; other errors → toast, the dialog stays open.

### Key decisions and why
- **Only what the API allows** (`canDistribute`, `allowedAnswers`, `allowedNextStatuses`): no client
  copy of the rules (they drifted in an earlier phase).
- **Native checkboxes in a Radix dialog**: a handful of platforms needs no search; checkboxes are the
  most accessible multi-choice control.
- **Distribute sits in the Distributions heading**, next to the table it changes (the plan had it next
  to the status control; moved during implementation because the status control says "final" for a
  distributed track while Distribute still applies there).
- **No-op detection**: the API answers 200 also when nothing changed; the dialog treats an unchanged
  `updatedAtUtc` as "already sent".
- **Badges never rely on colour alone**: the word and a different mark per status.

### How to run and test
Backend stack from a fresh database (`docker compose down -v` there), then `docker compose up --build`
here; sign in and open a submitted track. `npm test` (214, three runs green). Real-browser check (Edge
over DevTools, scratch script) on the compose stack, desktop light and 400 px dark: visitor sees
deliveries without controls; admin sees only "Withdraw to draft" on a submitted track; Distribute opens
with Enter and closes with Escape (focus returns); send two platforms; mark live and rejected; send the
rejected one again; send the last one → "Sent to every platform". No horizontal overflow, no app
console errors. Bundle 202 kB gzip.

### Known limitations
- Platform answers are simulated by the admin.
- The catalogue list does not show deliveries (only the track page does).
- Without seed data, deliveries exist only once created in the app or through the API.

### Follow-up: selects that follow the theme
Found by the developer in manual testing: native select lists were light grey with pale text in dark mode
(measured 1.49:1) and used the browser's light-blue/grey highlight.
- `src/components/ui/native-select.tsx` is the only component that renders a `<select>` (a test enforces it).
- `src/index.css` → "Selects" is the only place that styles them, with tokens only:
  1. every option gets `--popover` / `--popover-foreground` (fixes the unreadable list everywhere; it is
     also the fallback);
  2. inside `@supports (appearance: base-select)` (Chromium 135+: Edge, Chrome, Brave) the customizable
     select styles the open list, hover and keyboard-focused rows (`--highlight`, an accent tint), the
     selected row (checkmark + weight), disabled rows and a 2 px `--ring` focus ring. It is still a native
     `<select>`: Space opens, arrows move, typing jumps (e.g. "eg" → Egypt), Enter picks, Escape closes
     without changing; the accessibility tree is a combobox with options, `expanded` true when open.
- Plain CSS alone could not change the highlighted row of the classic popup (the browser draws it), hence
  the customizable select.
- Light `--ring` is now `#9a6500` (the saffron `#d99a0b` was 2.1–2.5:1 on light surfaces).
- The artist picker's active row uses the same `--highlight` plus an inset ring.
- Measured in Edge, dark, 1100 px: list text 13.8:1, highlighted row 9.32:1, closed select 12.83:1, focus
  ring 6.06:1 against the row. The full Edge/Chrome/Brave × light/dark × 1100/400 px matrix was still
  running when this was committed.
